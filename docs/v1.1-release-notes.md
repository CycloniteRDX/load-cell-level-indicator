# v1.1 Safe Startup Tare

## Release identifier

```text
v1.1-safe-startup-tare
```

## Release date

```text
2026-07-28
```

## Release status

This release resolves the most important operational safety problem remaining in `v1.0-functional-prototype`.

The firmware no longer performs an automatic tare during every startup. A validated tare offset is stored independently in EEPROM and restored after reset or power loss.

A container that remains partially filled during a restart is therefore measured relative to its previous operational zero instead of being silently redefined as empty.

## Problem resolved

The `v1.0` startup sequence performed:

```text
restart
    → wait
    → automatic tare
    → normal measurement
```

If power failed while a load was present, the restart treated that load as zero.

`v1.1` now performs:

```text
restart
    → load calibration factor
    → load persistent tare offset
    |
    +--> valid tare
    |       → restore offset
    |       → normal measurement
    |
    +--> invalid or missing tare
            → TARE_REQUIRED
            → normal level indication disabled
```

## Main capabilities added

### Persistent tare record

A new fixed-size tare record stores:

```text
4-byte magic
2-byte format version
4-byte signed tare offset
2-byte CRC-16/CCITT
```

The record is explicitly encoded in little-endian order and validated before use.

All `int32_t` offset values are representable, including negative values and the signed boundaries.

### Independent EEPROM layout

```text
EEPROM 0–11
    calibration record

EEPROM 12–23
    tare record

EEPROM 24 onward
    unused
```

Calibration and tare remain independent:

```text
calibration = ADC counts per gram
tare        = raw zero offset
```

Saving or clearing one record does not modify the other.

### TARE_REQUIRED

When no valid tare exists:

- Normal level indication is disabled.
- All three LEDs blink together slowly.
- The console explains how to establish zero.
- Calibration may still be started.
- A valid tare or calibration-zero confirmation restores normal operation.

### Deliberate physical tare

During normal operation:

```text
short D4 press
    → ignored

hold D4 for approximately 3 seconds
    → tare
    → EEPROM save
    → verification
```

The serial `t` command remains an immediate service operation.

### Stored-tare clear command

The new command:

```text
z
```

invalidates only the tare record and enters `TARE_REQUIRED` immediately.

The existing:

```text
x
```

continues to invalidate only the calibration record.

### Transactional failure behaviour

A manual or calibration tare follows this policy:

```text
preserve previous offset
    → collect candidate tare
    → save and verify EEPROM
    |
    +--> success
    |       → keep new offset
    |
    +--> failure
            → restore previous runtime offset
            → restore previous validity state
```

RAM and EEPROM therefore do not silently retain different operational zeros after a storage failure.

### Calibration integration

The calibration-zero stage now persists tare before advancing to the reference-mass stage.

If sampling or storage fails, calibration remains at zero confirmation.

If calibration is cancelled after a successful zero confirmation:

- The new tare remains stored.
- The previous calibration factor remains active.
- Both records continue to be independent.

### Button-context protection

D4 cancels calibration immediately.

The same physical press is then suppressed until release, preventing a long cancellation press from later being reinterpreted as a three-second tare.

## Upgrade behaviour from v1.0

The existing `v1.0` calibration record occupies EEPROM addresses 0–11 and is preserved.

`v1.1` adds its tare record at addresses 12–23.

The first startup after upgrading normally enters `TARE_REQUIRED` because no tare record has yet been created.

To complete the upgrade:

1. Leave the empty permanent container on the platform.
2. Hold D4 for approximately three seconds, or send `t`.
3. Wait for EEPROM verification.
4. Confirm that normal measurement begins.
5. Reset once and verify that the stored offset loads.

No calibration is required unless the existing calibration factor is no longer valid for the hardware.

## Physical validation

Confirmed on the physical Arduino Nano:

- Missing tare produces `TARE_REQUIRED`.
- All three LEDs blink together slowly in `TARE_REQUIRED`.
- Serial `t` stores and verifies tare.
- Stored tare loads after reset.
- A short D4 press does not tare.
- A three-second D4 hold tares exactly once.
- A load remains correctly measured after complete power loss and restart.
- Calibration can start from `TARE_REQUIRED`.
- Calibration zero confirmation persists tare.
- Complete calibration restores both records after restart.
- Holding D4 to cancel calibration does not later trigger tare.
- `x` clears only calibration.
- `z` clears only tare.
- Calibration and tare records remain independent.

Detailed evidence is recorded in:

```text
docs/v1.1-safe-startup-tare-validation.md
```

## Known limitations

This release intentionally retains:

- Blocking tare sample collection.
- Blocking calibration operations.
- One EEPROM slot per record.
- No EEPROM wear levelling.
- No stable-weight detector.
- No watchdog integration.
- No brown-out reset diagnosis.
- Serial service commands without confirmation.
- Compile-time thresholds and calibration mass.
- HX711 as the only measurement backend.
- ATmega328P Nano as the only production target.
