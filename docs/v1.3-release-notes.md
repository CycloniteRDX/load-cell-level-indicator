## Release date

```text

```

## Release status

This release adds bounded sensor recovery and hardware-watchdog supervision to
the cooperative `v1.2` application.

The firmware now distinguishes recoverable sensor faults from terminal
application or storage faults, disables normal level indication immediately,
attempts a finite HX711 recovery sequence and returns only to a safe application
boundary.

The release has passed native, build and physical validation. It does not add
measurement filtering, stable-weight qualification or a general-purpose reset
strategy for every terminal application fault.

## Main capabilities added

### Stable fault diagnostics

Application-visible fault codes `01` through `09` now have fixed meanings.
Each code maps to exactly one of:

```text
recover HX711
terminal reset-required state
```

Unknown codes normalize to the terminal internal-state fault. Existing code
numbers must not be renumbered by later releases.

### Status-rich scale reads

Normal weight acquisition distinguishes:

```text
new value
no conversion ready
driver/read error
```

The application can therefore supervise the absence of conversions without
confusing it with an immediate low-level read failure.

### Runtime readiness deadline

Every valid conversion renews a 2000 ms health deadline. If no conversion is
observed before the deadline, normal level indication is disabled and
`FAULT 03` begins cooperative recovery.

The deadline uses unsigned subtraction and remains correct across the
millisecond-counter overflow.

### Cooperative HX711 recovery

Recovery uses:

```text
500 ms backoff
real HX711 power-down/power-up
2000 ms readiness deadline
3 attempts maximum
```

No recovery state blocks the superloop. The LOW and HIGH LEDs alternate every
250 ms, button debouncers remain current, UART input receives an immediate
recovery response and rejected input is discarded.

A successful recovery:

- retains the previous committed tare and calibration;
- cancels unfinished sampling work;
- returns to normal operation or `TARE_REQUIRED` only at a safe boundary;
- never resumes an interrupted tare or calibration halfway through.

Exhausting all three attempts enters a latched terminal fault with the HIGH LED
blinking and a reset-required diagnostic.

### Transactional interruption guarantees

Physical fault injection proved the persistence boundaries:

- interrupted operational tare preserves the previous active and stored tare;
- interrupted calibration zero preserves the previous tare;
- a completed calibration zero remains committed if the later mass phase fails;
- interrupted reference-mass sampling preserves the previous calibration
  factor and does not create an EEPROM record.

### Persistent load classification

Calibration and tare loads now distinguish:

```text
valid
absent
invalid/corrupt
storage access failure
```

Absent or corrupt records follow their safe fallback policy. A real EEPROM
access failure enters terminal `FAULT 09` and is never misreported as a normal
first-start condition.

### Hardware watchdog

The ATmega328P hardware watchdog is configured for approximately two seconds.
It is enabled only after complete application initialization and is fed only
after a complete `app_update()` iteration returns.

There is no feed:

- from an interrupt;
- inside the application state machine;
- before the safe startup state exists.

The direct AVR and Arduino-reference entry points use the same feed boundary.
Dedicated validation builds provide a manual D4+D8 intentional-stall trigger
that is excluded from both production environments.

### Reset-cause diagnostics

An early AVR startup hook captures the reset flags still visible to the
application, clears them and disables an inherited watchdog before ordinary
initialization.

On the tested Nano bootloader path, no supported watchdog flag survives to the
application. Post-watchdog startup therefore reports `unknown`. Physical timing
still proves that the hardware watchdog performed the reset.

### Deterministic DOUT disconnection

The prototype now includes an external `10 kΩ` pull-up from Nano D2 to the
shared logic supply. It remains on the microcontroller side of the HX711
connection.

A broken or disconnected `DOUT` conductor consequently reads HIGH, the HX711
not-ready state, and produces a deterministic timeout. The current firmware
leaves the ATmega328P internal D2 pull-up disabled.

## Behaviour preserved from v1.2

- Startup never performs an automatic tare.
- Missing or corrupt tare data enters `TARE_REQUIRED`.
- Calibration and tare keep their existing EEPROM layouts.
- The direct AVR production build remains independent of Arduino Core.
- One `app_update()` remains a bounded cooperative step.
- Tare and calibration sampling still reads at most one ready conversion per
  update.
- D4 and UART cancellation remain available during multi-sample operations.
- The `v1.2` result-pattern input policy remains unchanged.
- No dynamic allocation or RTOS was introduced.

No EEPROM migration is required when upgrading from `v1.2`.

## Physical validation

The real Nano, HX711, load cell, buttons, LEDs and serial console passed:

- watchdog resets after `2.255 s` direct AVR and `2.260 s` Arduino reference;
- safe restart without a D4+D8 reset loop;
- deterministic DOUT disconnection using the external pull-up;
- automatic recovery after reconnection;
- exact terminal transition after three failed attempts;
- LOW/HIGH recovery and HIGH terminal LED patterns;
- a real `82.49783 us` PD_SCK power-down pulse with valid logic levels;
- at least 16 automatic power-cycle attempts across the physical matrix;
- interruption during tare, calibration zero and reference-mass collection;
- preservation of committed tare and calibration data;
- D4/D8 suppression and UART discard across recovery;
- normal tare, calibration start/cancel, persistence and measurement after all
  fault tests.

## Known limitations

- Recovery readiness proves that the HX711 produced a new conversion; it does
  not yet require several mutually coherent samples before declaring recovery.
- The external DOUT pull-up detects a missing digital connection but not every
  possible load-cell bridge-wire failure.
- Saturation, implausible measurement and advanced outlier detection remain
  outside the `v1.3` fault model.
- The Nano bootloader prevents reliable application-visible watchdog reset
  cause reporting on the tested path.
- EEPROM uses one slot per record and has no wear levelling.
- EEPROM writes and console transmission remain bounded synchronous work.
- Service commands do not require confirmation.
- Thresholds and reference mass remain compile-time values.
- The current production target remains the ATmega328P Nano with HX711.

## Next work

The next production milestone is measurement robustness. It should begin with
real raw-data capture and add only the simplest filtering, stability or outlier
policy justified by those measurements.

The separate educational repository can now document this stable milestone
after its existing `v1.2` Lesson 20 work is complete.
