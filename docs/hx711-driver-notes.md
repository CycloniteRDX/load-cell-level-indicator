# Custom HX711 Driver Notes

## 1. Purpose

The purpose of this branch is to replace the external Bogde HX711 library with a small custom HX711 driver.

The driver will be written primarily in C to improve understanding of:

* C structures.
* Pointers.
* Fixed-width integer types.
* Bitwise operations.
* Header and source files.
* Error handling.
* Hardware communication.
* Separation of concerns.

The driver will only handle low-level communication with the HX711.

Higher-level scale functionality will remain outside the driver.

---

## 2. Driver responsibilities

The custom HX711 driver will be responsible for:

* Configuring the HX711 data and clock pins.
* Checking whether a conversion is ready.
* Waiting for a conversion with a timeout.
* Reading the 24-bit conversion result.
* Converting the 24-bit two's-complement value into an `int32_t`.
* Selecting the HX711 channel and gain.
* Powering the HX711 down.
* Powering the HX711 up.
* Reporting communication errors to the caller.

---

## 3. Responsibilities outside the driver

The driver will not be responsible for:

* Converting raw ADC counts into grams.
* Calculating an average of multiple readings.
* Performing tare calculations.
* Storing the tare offset.
* Storing the calibration factor.
* Reading or writing EEPROM.
* Controlling LEDs.
* Handling buttons.
* Deciding the liquid level.
* Printing user messages.
* Implementing application logic.

These operations belong to higher-level modules.

The intended architecture is:

```text
Application logic
       |
       v
Scale or measurement module
       |
       v
Custom HX711 driver
       |
       v
HX711 hardware
```

This separation should make it easier to replace the HX711 with another ADC, such as the NAU7802 or ADS1232, without rewriting the complete application.

---

## 4. Why the driver will use C

The driver will use a procedural C interface instead of a C++ class.

The driver state will be stored in a structure:

```c
typedef struct
{
    uint8_t data_pin;
    uint8_t clock_pin;
    hx711_gain_t gain;
    bool initialized;
} hx711_t;
```

Functions will receive a pointer to this structure:

```c
hx711_status_t hx711_init(
    hx711_t *device,
    uint8_t data_pin,
    uint8_t clock_pin
);
```

The `device` pointer allows the function to access and modify the state of a particular HX711 instance.

No dynamic memory allocation will be used.

The caller will create the structure:

```c
hx711_t scale_adc;
```

The address of the structure will then be passed to the driver:

```c
hx711_init(&scale_adc, DATA_PIN, CLOCK_PIN);
```

The `&` operator obtains the memory address of `scale_adc`.

## 5. C and C++ compatibility

The Arduino application may still be compiled as C++, even though the driver is compiled as C.

The public header should therefore use the following structure:

```c
#ifndef HX711_DRIVER_H
#define HX711_DRIVER_H

#include <stdbool.h>
#include <stdint.h>

#ifdef __cplusplus
extern "C" {
#endif

/* Public C declarations */

#ifdef __cplusplus
}
#endif

#endif
```

When the header is included from C++, `extern "C"` tells the C++ compiler that the functions are implemented using C linkage.

When the header is included from C, the `__cplusplus` macro does not exist and the `extern "C"` lines are ignored.

## 6. HX711 physical interface

The HX711 uses two digital signals:

### DOUT

`DOUT` is the HX711 data output.

It has two purposes:

1. It indicates whether a conversion is ready.
2. It transfers the 24-bit conversion result.

When `DOUT` is HIGH, the conversion is not ready.

When `DOUT` becomes LOW, a new conversion result can be read.

### PD_SCK

`PD_SCK` is generated by the microcontroller.

It is used to:

* Clock the 24 result bits out of the HX711.
* Select the channel and gain for the next conversion.
* Put the HX711 into power-down mode.

`PD_SCK` should normally remain LOW while the driver is waiting for a conversion.

---

## 7. Basic reading sequence

A complete HX711 reading follows this sequence:

1. Make sure `PD_SCK` is LOW.
2. Wait until `DOUT` becomes LOW.
3. Generate 24 clock pulses.
4. Read one data bit during each clock pulse.
5. Store the bits from most significant bit to least significant bit.
6. Generate one, two or three additional clock pulses.
7. Convert the 24-bit result into a signed 32-bit value.
8. Return the result to the caller.

The HX711 sends the most significant bit first.

The bit-reading operation can be represented conceptually as:

```c
raw_value = raw_value << 1;

if (data_pin_is_high)
{
    raw_value = raw_value | 1U;
}
```

The left shift makes space for the next bit.

The bitwise OR operation stores a `1` in the least significant position when the data pin is HIGH.

---

## 8. Channel and gain selection

After reading the 24 data bits, the microcontroller must generate additional clock pulses.

The number of additional pulses selects the channel and gain for the next conversion.

| Total clock pulses | Additional pulses | Channel | Gain |
| -----------------: | ----------------: | :-----: | ---: |
|                 25 |                 1 |    A    |  128 |
|                 26 |                 2 |    B    |   32 |
|                 27 |                 3 |    A    |   64 |

The first version of the project will use:

```text
Channel A
Gain 128
25 total clock pulses
```

The driver API may support all three configurations, but the initial integration will use channel A with gain 128.

The gain may be represented with an enumeration:

```c
typedef enum
{
    HX711_GAIN_A_128 = 1,
    HX711_GAIN_B_32  = 2,
    HX711_GAIN_A_64  = 3
} hx711_gain_t;
```

The numeric values correspond to the number of additional clock pulses.

Using an enumeration makes the code more readable than using unexplained numbers such as `1`, `2` or `3`.

---

## 9. Signed 24-bit conversion

The HX711 produces a signed 24-bit value using two's-complement representation.

C does not normally provide an `int24_t` type.

The driver will first store the 24 received bits in a `uint32_t`:

```c
uint32_t raw_value = 0U;
```

The most significant bit of the 24-bit value is the sign bit.

Its mask is:

```c
0x00800000UL
```

If this bit is `0`, the value is positive.

If this bit is `1`, the value is negative.

To convert a negative 24-bit value into a negative 32-bit value, the upper eight bits must also be set to `1`:

```c
if ((raw_value & 0x00800000UL) != 0U)
{
    raw_value |= 0xFF000000UL;
}
```

The result can then be interpreted as an `int32_t`:

```c
int32_t signed_value = (int32_t)raw_value;
```

This process is called sign extension.

Without sign extension, a negative HX711 reading would incorrectly appear as a very large positive value.

## 10. Timeout handling

The driver must never wait forever for the HX711.

The following implementation would be unsafe:

```c
while (digitalRead(data_pin) == HIGH)
{
}
```

If the HX711 is disconnected, incorrectly wired or damaged, the complete application would remain blocked inside the loop.

The driver will instead provide a timeout:

```c
hx711_status_t hx711_wait_ready(
    const hx711_t *device,
    uint32_t timeout_ms
);
```

The function will return an error when `DOUT` does not become LOW before the timeout expires.

Possible results include:

```c
typedef enum
{
    HX711_STATUS_OK = 0,
    HX711_STATUS_INVALID_ARGUMENT,
    HX711_STATUS_NOT_INITIALIZED,
    HX711_STATUS_TIMEOUT
} hx711_status_t;
```

Using a status enumeration provides more information than returning only `true` or `false`.

## 12. Pointer usage

The driver uses pointers for two main reasons.

### Device pointer

Functions receive a pointer to an `hx711_t` structure:

```c
hx711_status_t hx711_init(hx711_t *device, ...);
```

This allows the function to modify the actual structure owned by the caller.

For example:

```c
device->data_pin = data_pin;
device->clock_pin = clock_pin;
device->initialized = true;
```

The `->` operator accesses a structure member through a pointer.

It is equivalent to:

```c
(*device).data_pin = data_pin;
```

The `->` form is easier to read.

### Output pointer

The raw reading is returned through another pointer:

```c
hx711_status_t hx711_read_raw(
    hx711_t *device,
    int32_t *raw_value
);
```

When the reading succeeds, the function writes the result into the caller's variable:

```c
*raw_value = signed_result;
```

This allows the function to return an error status separately.

Example usage:

```c
int32_t reading = 0;

hx711_status_t status = hx711_read_raw(&scale_adc, &reading);

if (status == HX711_STATUS_OK)
{
    /* reading now contains the ADC result */
}
```

## 13. Private helper functions

Functions that are only used inside `hx711_driver.c` should be declared with `static`.

Example:

```c
static bool hx711_gain_is_valid(hx711_gain_t gain);
```

In this context, `static` means that the function is private to the current `.c` file.

It cannot be called directly from another source file.

Possible private helpers include:

```c
static bool hx711_gain_is_valid(hx711_gain_t gain);

static void hx711_generate_clock_pulse(const hx711_t *device);

static void hx711_generate_gain_pulses(const hx711_t *device);

static int32_t hx711_sign_extend_24_bits(uint32_t raw_value);
```

These helpers should not appear in the public header.

---

## 14. Use of `const`

A pointer should use `const` when the function does not need to modify the pointed-to structure.

Example:

```c
bool hx711_is_ready(const hx711_t *device);
```

This communicates that `hx711_is_ready()` only reads the driver state.

The compiler will report an error if the function accidentally tries to modify a member through this pointer.

A function that changes the driver state should not use `const`:

```c
hx711_status_t hx711_set_gain(
    hx711_t *device,
    hx711_gain_t gain
);
```

---

## 15. Use of `volatile`

The initial driver structure will probably not require `volatile`.

`volatile` should not be added automatically to hardware-related variables.

It is normally needed when a value can change outside the normal flow of the current code, such as:

* A variable modified by an interrupt service routine.
* A memory-mapped hardware register.
* A variable modified by another execution context.

The HX711 result variable is filled by normal program instructions, so it does not need to be declared `volatile`.

The GPIO implementation provided by the platform handles access to the actual hardware registers.

---

## 16. Timing considerations

The duration of the HIGH part of a normal `PD_SCK` pulse must remain short.

If `PD_SCK` remains HIGH for more than approximately 60 microseconds, the HX711 enters power-down mode.

An interrupt occurring while `PD_SCK` is HIGH could accidentally extend the pulse.

The implementation must therefore consider how to protect the clock sequence.

Possible approaches include:

1. Disabling interrupts during the complete 24-to-27-pulse sequence.
2. Disabling interrupts only around each HIGH-to-LOW clock pulse.
3. Saving and restoring the previous interrupt state.
4. Using a small platform-specific critical-section helper.

The selected solution should:

* Keep the critical section as short as possible.
* Avoid accidentally enabling interrupts that were already disabled.
* Keep the driver understandable.
* Avoid premature hardware-specific optimization.

The first implementation will prioritize correctness and clarity over maximum speed.

---

## 17. Arduino platform dependency

The driver logic should be written in C, but it still needs platform functions for:

* Configuring GPIO pins.
* Reading a GPIO pin.
* Writing a GPIO pin.
* Measuring elapsed milliseconds.
* Entering and leaving a critical section.

The simplest implementation may call Arduino-compatible functions directly.

If the Arduino headers cannot be cleanly included from a `.c` file, a small C++ platform bridge may be added.

For example:

```text
hx711_driver.c
    Pure C driver logic

hx711_platform_arduino.cpp
    Small wrapper around Arduino GPIO and timing functions
```

The bridge would expose functions with C linkage:

```c
void hx711_platform_write_pin(uint8_t pin, bool level);
bool hx711_platform_read_pin(uint8_t pin);
uint32_t hx711_platform_millis(void);
```

This would allow the main driver to remain written in C even though the Arduino framework itself uses C++.

The bridge should only be added if it is actually necessary.

---

## 18. Power control

The HX711 enters power-down mode when `PD_SCK` is held HIGH for more than approximately 60 microseconds.

The power-down sequence will be conceptually:

```text
Set PD_SCK LOW
Set PD_SCK HIGH
Keep it HIGH for at least 60 microseconds
```

To power the HX711 up again:

```text
Set PD_SCK LOW
```

After power-up, the driver may need to wait for a new conversion before reading data.

The selected gain must also be restored or confirmed after power-up.

## 21. Implementation order

The driver should be implemented incrementally.

### Step 1: public types and initialization

Implement:

```c
hx711_init()

```

Verify that:

* The clock pin is configured as an output.
* The data pin is configured as an input.
* The clock pin starts LOW.
* Invalid pointers are rejected.

### Step 2: timeout

Implement:

```c
hx711_wait_ready()
```

Verify that:

* The function returns successfully when `DOUT` becomes LOW.
* The function returns a timeout error when the HX711 is disconnected.
* The application does not freeze.

### Step 3: raw reading

Implement:

```c
hx711_read_raw()
```

Verify that:

* Exactly 24 data bits are read.
* The bits are read most significant bit first.
* The additional gain pulse is generated.
* Sign extension is correct.

### Step 4: gain selection

Implement:

```c
hx711_set_gain()
```

Verify that only valid enumeration values are accepted.

### Step 5: power control

Implement:

```c
hx711_power_down()

```

### Step 6: integration

Replace the Bogde library calls inside the scale module.

The application behavior should remain unchanged.

### Step 7: dependency removal

Remove the Bogde HX711 dependency only after the custom driver has been tested successfully.

## 24. Initial design decisions

The initial design decisions are:

* Use C for the main HX711 driver implementation.
* Use a structure and procedural functions instead of a C++ class.
* Use fixed-width integer types from `<stdint.h>`.
* Use `bool` from `<stdbool.h>`.
* Avoid dynamic memory allocation.
* Use explicit status codes for errors.
* Use output pointers for returned measurements.
* Support channel A with gain 128 first.
* Add timeout handling from the beginning.
* Keep calibration and tare outside the low-level driver.
* Prefer readable GPIO operations before direct register access.
* Add a small Arduino C++ bridge only if required by the build system.

The custom driver was tested using an Arduino Nano, an HX711 module and the current provisional mechanical platform.

This value is not considered a final calibration result because the current mechanical platform is provisional.
